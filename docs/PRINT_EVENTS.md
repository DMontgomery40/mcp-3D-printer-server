# Print observations and MCP Events

Print event support is optional and disabled by default. It does not change printer safety gates or create a printer connection, network listener, credential, subscription, or background worker.

## Working with existing clients

Set `MCP_PRINT_EVENT_STORE` to an absolute path in a private local directory **outside the checkout** whose parent already exists. Configure the default Bambu host and serial as usual. Use a different journal for each server process; only one writer may open a journal. The journal and lock use mode 0600. On normal exit the lock is removed; after an abrupt crash, confirm that the previous process exited before manually removing the `.lock` file. Invalid configuration, a locked journal, or corrupt storage disables optional capture with a generic diagnostic; printer controls still start. Repair storage before restarting. History is never silently discarded.

The read-only `list_print_events` tool reports a disabled error until recording is enabled. It accepts `cursor` (default `"0"`) and `limit` (1–100, default 100). Save the returned cursor and supply it to the next call. `truncated: true` means some requested history was pruned. The journal retains the most recent 1000 events. This is a local history tool; it does not subscribe ChatGPT or wake an inactive session.

Capture starts when another operation opens a default-printer MQTT status connection, and lasts while that process and connection remain alive. Only actual `push_status` reports on the configured printer's report topic are observed. Other printer targets and non-Bambu adapters do not produce events. Deltas received on an existing connection are merged; reconnects clear that transient snapshot, so a new connection must supply fresh job identity. MQTT has no durable upstream event log: a print that starts and ends entirely while the server is absent cannot be recovered. A persisted armed job can finish after reconnect/restart once its identity is reported again.

`print.completed` requires an observed PREPARE, RUNNING, or PAUSE job and a matching FINISH report. Initial FINISH, 100% progress, IDLE, cancellation, FAILED, or a job with current actionable errors never becomes successful completion. A recovered job may finish after its errors explicitly clear. A local stop request suppresses completion even if the command later fails. Fault codes are deduplicated per observed job; errors clearing and reappearing do not repeat. HMS severity 4 is informational and ignored, matching the print safety gate. Unknown/malformed telemetry does not invent fault details. Sparse or unidentified reports can cause an event to be withheld; this feature favors avoiding false success over guessing.

Payloads contain an opaque job UUID, the alias `default`, occurrence time, and numeric fault codes/reasons. They contain no host, serial, access code, filename, raw MQTT record, or stack trace. `print.problem` reports printer telemetry, not a diagnosis. Failed event storage disables capture and causes history reads to fail, while emergency controls remain available.

## Optional real MCP 2.0 host

The current dependency is `@modelcontextprotocol/sdk` 1.x, which uses `initialize` and accepts protocol versions through 2025-11-25. It cannot honestly advertise MCP 2.0 (`2026-07-28`) through a hand-written `server/discover` response: subsequent requests carrying that version are rejected by its HTTP transport. Existing HTTP endpoints also do not establish an authenticated subscription owner.

The official [OpenAI MCP Events guide](https://developers.openai.com/plugins/build/mcp-events) requires MCP 2.0 discovery, `events/list`, `events/subscribe`, and `events/unsubscribe` on the authenticated tools endpoint, persistent subscriptions, and verified signed outbound HTTPS callbacks. ChatGPT supports webhook delivery; session resource updates, polling, and streaming are not substitutes for durable wakeups. The [MCP Events design sketch](https://github.com/modelcontextprotocol/experimental-ext-triggers-events/blob/main/docs/design-sketch-proposal.md) remains a draft; this module follows the OpenAI webhook subset.

`events-host/` supplies a separate **real SDK 2.2.0** host using `@modelcontextprotocol/server` and the Node adapter. It leaves existing SDK 1.x transports and printer controls intact. Its `/mcp` endpoint serves actual SDK `server/discover`, read-only history/minimal-state tools (without raw printer identifiers), and `events/list`, `events/subscribe`, and `events/unsubscribe` under one authenticated principal. It rejects legacy protocol requests and browser origins and validates Host headers. Existing stdio/desktop clients keep using their original endpoint; they do not gain durable push merely by upgrading this package.

Install the separate host dependencies with `npm --prefix events-host ci` after building the root server. The explicit host command is `npm --prefix events-host start`. It requires:

- `MCP_EVENTS_HOST_STORE`: absolute private host journal path outside the checkout, parent already present. The legacy child uses a different `${MCP_EVENTS_HOST_STORE}.printer` journal.
- `MCP_EVENTS_AUTH_MODULE`: absolute path to an operator-provisioned module exporting `authenticate(request)`, `authorize({principal}, "default")`, and `oauthMetadata` for an existing OAuth 2.1 authorization server. Authentication must validate token signature/introspection, issuer, expiration, audience bound to this resource, and read scope. Return `{principal, clientId?}` only after verification; principal is a stable issuer/user account identity, never a shared OAuth client ID, request metadata, printer token, or unsigned JWT claim. Authorization must support revocation and account-to-printer mapping.
- `MCP_EVENTS_PUBLIC_URL`: approved public `https://…/mcp` resource URL. The host advertises official SDK OAuth Protected Resource Metadata and `WWW-Authenticate` discovery, and returns 403 when an authenticated owner lacks access.
- Optional `MCP_EVENTS_HOST_PORT` (default 3001): binds **127.0.0.1 only**. A separately approved HTTPS reverse proxy or supported tunnel must forward the MCP endpoint and OAuth metadata routes. No printer MQTT/FTPS ports should be exposed.

The host starts an isolated local stdio child with the existing printer safety code, opens the default-printer MQTT observation connection with a status read, refreshes it at most every five minutes, imports journal events with an atomic source watermark, and runs bounded delivery iterations every 15 seconds. Status/relay failures do not prevent delivery of already persisted events. This is local monitoring behind a webhook host, not ChatGPT polling. Import rejects a retention gap instead of skipping lost events. Callback delivery and owner authorization remain independent of a foreground chat. Graceful shutdown waits for pending work before closing the journal; a process crash leaves a lock requiring operator reconciliation.

**Deployment still needs approval:** select/provision the existing OAuth provider and account policy; register the ChatGPT OAuth client/resource if required; expose only the approved read-only HTTPS host; install/rescan the plugin/connection so ChatGPT discovers `capabilities.events`; then explicitly create the desired automation/subscription. No production verifier, credential, public listener, OAuth registration, or external subscription is created by this development change. The local tests use a test-only verifier and in-memory signed callback receiver. They demonstrate real MCP2 protocol handling and callback acceptance, not a live ChatGPT wakeup.

The service stores deterministic owner-scoped subscription identities, callback URL/secret, expiration, acknowledged cursor, and retry state. The default callback sender requires public HTTPS on port 443, validates DNS at every connection, pins a validated IP while preserving hostname/TLS verification, rejects all nonpublic results and redirects, and bounds requests/responses. Verification challenges are signed and compared in constant time before activation. Successful verification is cached for five minutes per subscription/secret. A replacement secret is verified and receives a five-minute dual-signature rotation window.

Each journal observation has a stable ID. Outbound event IDs are deterministically scoped to the subscription and observation, preserving the same body `eventId` and `webhook-id`, so different subscriptions cannot collide in receiver deduplication. Each delivery has a stable serialized body across retries; each retry gets a fresh signing time/signature. Delivery is at least once; receivers must deduplicate `webhook-id`. A 2xx acknowledges receipt, not completion of a ChatGPT automation. Transient failures use exponential backoff with eight total attempts; 410, 413, permanent client errors, or exhausted attempts stop that subscription. The host/operator must surface stopped subscriptions. Expiration and revoked access remove subscriptions. This server grants at most a one-day lifetime (including `ttlMs: null`, which is granted as finite), and refresh cannot skip pending events. Replay uses the journal's sequence cursor. If retention evicts an unacknowledged matching event, delivery stops instead of advancing past it; refresh reports `truncated: true`. Pending deliveries beyond retained history cannot be recovered.

Tests use synthetic MQTT lifecycle transitions, actual SDK2 discovery/authorization/event requests, and an independent HMAC-verifying simulated callback receiver. Automated tests do not contact a real printer or external callback. Maintainer physical validation uses one 8 × 8 × 1.2 mm PLA tile (0.19 g) on a P1S with a hardened-steel 0.4 mm nozzle. Fresh bed/state/material checks pass before its official authenticated Bambu Studio dispatch. Both development servers observe exactly one completion on matching FINISH, with no problem events; repeated reads and an observer reconnect preserve that result. Each actual observation also passes real SDK2 subscription and independent in-memory signed callback acceptance, duplicate import, and acknowledged-delivery restart checks. Problem events are tested synthetically. A real ChatGPT subscription lifecycle remains required before claiming live ChatGPT wakeups. No release or publication is part of this development change.
